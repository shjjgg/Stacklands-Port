> 原则：**编辑器/导出/反编译工具链围绕 Unity 2022.3.4f1 对齐**；版本错配会导致 TypeTree、序列化格式、shader blob 解析偏差。版本号以“能正确打开 2022.3.4f1 资产”为准，安装后先做版本校验。

## 2. Unity Editor（2022.3.4f1）

### 2.1 安装模块

- Unity Hub 添加版本 **2022.3.4f1**。
- 必须勾选模块：
  - **Android Build Support**
    - SDK / NDK / OpenJDK（用引擎自带推荐版本，不手动换 NDK）
  - （可选）Vulkan 渲染验证所需组件
- 确认 `ProjectSettings` 中脚本运行时为 .NET 4.x，与原版一致。

### 2.2 校验

- 新建工程打开后，Editor 标题/`Application.unityVersion` 为 `2022.3.4f1`。
- 能正常导入 AssetRipper 导出工程，无 “version mismatch” 致命报错。

## 3. AssetRipper 工程重建

1. 选用明确支持 2022.3 的 AssetRipper 版本；先用 `tools/reconstruct_source.py` 还原数据目录。
2. 打开还原后的 `Stacklands_Data`，导出为 Unity 工程；开启脚本反编译。
3. 按 `docs/10_AssetRipper导出校验清单.md` 核对数量基线、脚本绑定、资源链。
4. 注意：AssetRipper 自带 shader 反编译**仅作参考**，不直接采信（见 03）。

## 4. C# 反编译回填

- 目标程序集：`GameScripts.dll`（主逻辑，353 类）、`Assembly-CSharp.dll`、`Assembly-CSharp-firstpass.dll`、`csS.dll`。
- 用 dnSpy/ILSpy 打开 `Stacklands_Data/Managed/` 下对应 DLL，对照 AssetRipper 导出的脚本桩回填源码。
- 第三方托管（ShapesRuntime/SokLoc/SokSheet/Sirenix/DOTween/Newtonsoft）优先取官方源码或原版预编译 DLL，不手工反编译改写。
- 反编译后跑 `tools/scan_il2cpp_risks.py` 定位 Emit/Roslyn/反射/Harmony 命中。

## 5. Shader 工具链落地顺序

1. **blob 提取**：已由 `tools/extract_shader_blobs.py` 完成，产出 `shader_extract/blobs/*.blob` 与台账。
2. **ShaderRipper**：对每个自研 blob（30 个，见 03 台账）拆分变体、常量缓冲、采样器槽位、关键字。
3. **3Dmigoto HLSLDecompiler**：输出原始 HLSL；保留寄存器/原名/控制流，不美化。
4. **spirv-cross**：按 Vulkan SPIR-V / GLES GLSL 交叉转换。
5. **手工补全**：宏、Pass、Tags、贴图绑定、CBUFFER 字段顺序；回 blob 字节核对。
6. **RenderDoc**：PC 原版与 Android 包同机位抓帧比对。

## 6. 原生/平台相关工具

- 本工程源端为 **Mono**，不需要对源程序集做 IL2CPP dump；IL2CPP 仅在目标出包时生成，符号用于崩溃堆栈还原。
- Steamworks.NET / cimgui 原生库为 Windows PE，不参与 Android 构建；桩接见 05、09。
- 如需分析原生 PE（可选）：PE 查看器核对导出表；不作为移植必需项。

## 9. 静态门的已知边界

`tools/lint_unity_api_usage.py` 是纯文本分析，不是编译器。它能证明的事和不能证明的事要分清：

- **能拦**：缺 `using`、用了白名单外的 `Type.Member`、括号不配对、`#if UNITY_EDITOR` 缺失、重复 `public static` 方法名，以及**字符串插值表达式内**的成员访问（本轮已补：`$"...{summary.totalSize}B"` 这种写法以前会被整段抹掉）。
- **不能拦**：重载解析歧义、泛型约束不满足、`var` 推断失败后的连锁错误、反射/宏展开、运行期才会暴露的问题。
- 因此**它只能把"必然编译不过"提前到 CI，不能替代 Unity 的真实编译**。工程落地后的首次 `StrictBuild` 仍是唯一可信的编译验证。

## 10. Shader blob 的真实结构（一处重要更正）

上一版把 `shader_extract/blobs/*.blob` 直接当作"ShaderRipper 输入"，**这是错的**：

- `.blob` 是 Unity 的 **LZ4 压缩容器**。以 `Custom/ArrowSdfShader` 为例：4889 B → 解压 42628 B。
- 解压后是程序表，里面装着 **15 段 D3D11 字节码**（VS 8 / PS 7），每段都是标准 DXBC（`ISGN`/`OSGN`/`SHDR` 三个 chunk）。
  在压缩态里直接 `grep DXBC` 只会看到 1 个（那是未压缩的清单区），会误判"每个 shader 只有一段"。
- 因此保真链的第①步输入必须是 `shader_extract/dxbc/<name>__<idx>_<stage>.dxbc`，
  由 `tools/extract_dxbc_programs.py` 按 typetree 的 `offsets / compressedLengths / decompressedLengths`
  逐段 `lz4.block.decompress` 后，再按 DXBC 头（chunkCount、totalSize、chunk 表越界校验）切片。
- **DXBC 里没有 `RDEF` chunk**：Unity 剥掉了反射信息，所以字节码里拿不到资源名/绑定点。
  资源映射只能来自 Shader 资产的 `m_ParsedForm`（属性表 + name indices），不能靠字节码反推。

实测口径（30 个自研/改编 shader）：压缩 173 KB → 解压 1.6 MB，共 **504 个程序段**，
零解压失败、零非法头，且**每个 shader 都同时含 VS 与 PS**。

> 这里踩过一个坑并已修：切片器原来默认 `--max-programs 64`，`Custom/CardBackShader` 有 66 段，
> 被**静默截断**成 64（PS 少 2 段）。是"typetree 变体数 ↔ DXBC 段数对账"（§10.3）把它抓出来的，
> 现在上限 4096，且触顶会显式报警。

这条程序段数是重建验收的硬参照：重建后编译出的程序段数明显少于原版，就说明关键字/变体被吃掉了。

### 10.1 签名块（ISGN / OSGN）能解出什么

DXBC 里没有 RDEF，但**签名块是完整的**，`tools/extract_signatures.py` 按
`count(4) + strtab_off(4) + 每元素 24B(名字偏移/语义索引/系统值/类型/寄存器/读写掩码)` 解析。

实测 30 个 shader 的结论：

| 类别 | 顶点输入 | 插值通道 | 备注 |
|---|---|---|---|
| SDF 箭头/线缆族 | `POSITION@r0, TANGENT@r1, NORMAL@r2, TEXCOORD@r3, TEXCOORD1@r4, TEXCOORD2@r5, TEXCOORD3@r6, COLOR@r7` | 5 | 8 个输入全用到，4 组 UV 通道 |
| 卡面族（CardBack/CardShaderTest） | 上述 8 个 + `SV_InstanceID@r8` | 15 / 18 | 含实例化变体 |
| Transition 族 | 8 个（无 SV_InstanceID） | 4 | 4 个变体布局一致 |
| Sprites / Unlit / Postprocess | 2–3 个 | 2–3 | 极简 |

- **VS 输出 ↔ PS 输入 链接：30/30 干净**（无"仅 VS""仅 PS"通道，掩码一致）。
  这是原版的正常状态；重建后若出现单向通道，就是插值错乱/粉色块的根因。
- `SV_InstanceID` 只出现在实例化变体里，布局比较时必须排除，否则会误报"变体布局不一致"（本轮踩过）。

### 10.2 Pass 渲染状态（HLSL 之外的另一半）

保真链只还 HLSL 是不够的：同一段 fragment 配上错的 `ZWrite`/`Blend`/`Cull`，画面就是另一种东西。
这些状态只在 Shader 资产的 `m_State` 里，`tools/extract_pass_state.py` 全量导出：

- 30 个 shader / 58 个 pass，**去重后只有 14 种状态组合** —— 意味着只需要验证 14 份 ShaderLab 状态。
- 主要组合：`ZTest LEqual + ZWrite On`（20 个 pass，不透明）、`ZTest LEqual + ZWrite Off + Blend One One`（9 个，叠加发光）、
  `ZTest Disabled + Blend SrcAlpha OneMinusSrcAlpha + ColorMask GBA`（4 个，UI/描边类）。
- 枚举映射经交叉验证：最常见的 `Blend (5,10)` 解出 `SrcAlpha / OneMinusSrcAlpha`，若顺序错位这个组合不可能对上。
- 反常规项已单独列在 `pass_state.md`，例如：
  - **`ColorMask GBA`**：红色通道不写（SDF 描边族普遍如此，可能是把红通道留给别的 pass）;
  - **`Cull Off + ZWrite On + ColorMask 0`**：只写深度、不写颜色（典型的阴影/遮罩 pass）;
  - `ZTest Disabled` 出现在线缆/管道的部分 pass 上。
  这些都要按原版原样复刻，不能"顺手改正常"。

### 10.3 变体预算与对账（防止"少几段却看不出来"）

`tools/extract_variants.py` 读 Shader 的 `m_PlayerSubPrograms` 得到每个 pass 的变体清单，
再与 `dxbc_ledger.json` 的段数逐 shader 对账：

- **30/30 一致**：`typetree 变体数 == DXBC 切出的程序数`。这条等式是"切片没丢程序"的证明。
- 逐 pass 明细给出：VS/PS 变体数、`ProgramMask`、是否实例化变体（`m_HasInstancingVariant`）。
- 该对账在 CI 里跑，不一致直接红：链条有洞时不允许继续谈重建。

### 10.4 阶段判定的独立证伪

切片器判 VS/PS 靠 SHDR 版本 token，而文件名又由该判定生成——这是**自证循环**：
token 解析错一处，504 个文件名会整齐地一起错，且彼此"自洽"。

`tools/verify_stage_semantics.py` 换一条完全与 token 无关的判据：

- VS 的 OSGN 必须写 `SV_Position`，且不得出现 `SV_Target*`/`SV_Depth`；VS 必须有 ISGN；
- PS 的 OSGN 必须含 `SV_Target0..7` 或 `SV_Depth*`，且不得写 `SV_Position`；
- 同时仍校验 token 与文件名一致（两者都过才算干净）。

实测：**504/504 通过**，阶段分布 VS 244 / PS 260，零反例。产出 `stage_semantics.{md,csv,json}`，CI 强制。

### 10.5 关键字矩阵（重建"允许少程序，不允许少 keyword"）

`tools/extract_keyword_matrix.py` 读 `m_KeywordNames`，按互斥组展开理论上界，再与 `dxbc_ledger` 实际段数并列：

- 20 个 `Custom/` shader 全部携带**同一套 25 个内置关键字**（4 个 STEREO_* + INSTANCING_ON + 雾/光类型/阴影/光照贴图/顶点光照/HDR/EDITOR_VISUALIZATION），最重的 `CardBackShader` 26 个。
- 理论上界 15.36 万（CardBack 23.04 万）对实际 15–66 段，覆盖率 1e-4 量级。这**不是**缺陷：Unity 构建时按平台与 keyword 组合裁剪，只保留真正被实例化到的程序。
- 因此重建的验收口径是：**keyword 名字集合不得少于本表**（拼错 = 该分支永远不生效，且编译器不报错），互斥组每个分支至少能编出一条程序；而不是去凑上界段数。
- 平台强制项（`STEREO_*`、`INSTANCING_ON`）在 Android 单通道立体/实例化下会真实命中，必须在 `multi_compile_instancing` 与 stereo 宏中保留。

### 10.6 ShaderLab 保真校验（重建落地后唯一能机器验的一层）

`tools/verify_shaderlab_fidelity.py` 把重建的 `.shader` 与三张台账逐项对账，四条断言全部硬失败：

1. **覆盖**：台账里 30 个 shader 都必须存在同名文件，`Custom/` 族不少于 20 个；
2. **Pass 数**：每个 SubShader 的 pass 数必须与 `pass_state.json` 逐位置相等；
3. **渲染状态**：`Cull / ZTest / ZWrite / Blend / ColorMask / AlphaToMask / Offset / Stencil` 规范化后与台账 `shaderlab` 片段**逐字相等**——包括 `ColorMask GBA`、`ColorMask 0`、`ZTest Disabled` 这些反常规项，不允许“顺手改正常”；
4. **关键字**：`#pragma multi_compile*/shader_feature*` 声明的名字集合必须 ⊇ `keyword_matrix.json`；`INSTANCING_ON` 允许由 `multi_compile_instancing` 隐式覆盖。

自测（CI 每次跑）：用台账自身合成"必然正确"的样本，再打四个变异——错 blend、少一个 pass、少一个 keyword、`ColorMask GBA→RGBA`——四类全部被精确抓到后才算校验本身可信。当前 `Assets/Shaders` 为空，真实校验处于 skip 状态。

### 10.7 保真总表（验收闭包）

`tools/build_fidelity_table.py` 把 dxbc / signature / pass_state / variant / keyword / worklist 六张台账压成 **一个 shader 一行**：

| 列 | 含义 | 硬要求 |
|---|---|---|
| `VS/PS` | 程序段数 | 必须等于 typetree 变体数（§10.3 已证 30/30） |
| 顶点输入 / 插值 | VS 输入类别数、插值通道数 | 与原版一致才有资格谈 HLSL 结构 |
| 链接 | VS 输出 ↔ PS 输入 | 必须 clean（当前 30/30 干净） |
| pass / 状态组合 | pass 数、去重状态编号 | 与 `pass_state.json` 逐位置一致 |
| 关键字 | 关键字个数 | 不得少于矩阵（§10.5） |
| 风险 | 汇总异常 | **非空即禁止开工** |

当前实测：30 shader / 504 程序（VS 244 / PS 260）/ 风险 0。总表随 CI 每次重建，`risk` 列是开工前唯一需要扫的一列。

### 10.8 重建规格书（spec/ 每 shader 一份）

`tools/extract_shader_spec.py` 把原始数据收成 `shader_extract/spec/<名>.json`，它是重建的**数据契约**（不是可编译 shader）：

- `properties`：属性名/显示名/类型/默认值/标志位，贴图带 `dim`——素材参数名拼错就取不到值；
- `fallback` / `dependencies` / `subshaders[].tags`（`QUEUE`、`RenderType`）——决定降级与渲染队列；
- `passes[]`：每个 pass 的 `lightmode` + 规范化状态行（与 `pass_state.json` 同源）；
- `programs`：段数 VS/PS（与 typetree 变体数已证一致）；
- `vertex`：VS 输入类别数、插值通道、是否实例化变体；
- `keywords` / `platform_forced`。

实测 30 份，属性合计 **256**、pass 合计 **58**（与台账一一对应）。`verify_shaderlab_fidelity.py` 已把 spec 接进校验：属性名缺失、`Fallback` 不一致都会硬失败，自测新增两例后共 **7 例全通过**。

### 10.9 DXBC 指令级反汇编（语义骨架的唯一来源）

Unity 剥掉了 HLSL 源码和 RDEF 反射，所以"原版到底算了什么"只能从 SM5 字节码读。
`tools/disassemble_dxbc.py` 解析 SHDR 指令流，编码依据固化在 `docs/dxbc_opcodes.json`
（106 条 opcode，取自 wine-6.0 `dlls/wined3d/shader_sm4.c`，含 handler 与操作数签名）。

长度语义（踩过一次坑）：opcode token 的 bit24-28 是**整条指令占用的 dword 数（含 opcode token）**，
为 0 时紧随一个 dword 给出同样含义的总长度；SHDR 的 `length` 字段**包含 version+length 两个 dword**，
所以校验等式是 `指令流消费 == length - 2`。首版按"不含 opcode"理解，504 个程序全部差 2。

实测：**504 程序 / 42,036 条指令 / 未知 opcode 0 / 长度不符 0**。按 shader 汇总给出：

- 指令数与不同 opcode 数（`CardShaderTest` 7,124 条指令 / 45 种 opcode 最重）；
- Top opcode 频次（`MAD/MUL/ADD/DP3` 主导，说明是标准光照+数学，无奇异控制流）；
- `dcl` 实际绑定的 **cbuffer / texture / sampler 索引**（Unity 标准 9 个 cbuffer 0–8 全覆盖）。

`--asm <shader>` 可导出人类可读清单（`shader_extract/asm/`），F1 族 `ArrowSdfShader` 已导出 15 份作为样板。
